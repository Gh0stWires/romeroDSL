# romeroDSL v0.5 Finish Plan

> **For Hermes:** Use test-driven-development while implementing this plan. This plan is being executed in the same turn because Sam asked for a fully finished v0.5, not plan-only mode.

**Goal:** Finish v0.5 as the mapper-quality geometry/authorship milestone after the v0.4 HOM/material milestone.

**Architecture:** Keep the semantic DSL as the source of truth. Extend the sector-primitive compiler so authored shapes and height features become safer Doom geometry, then verify with unit tests, WAD validation, and Zandronum using the real `DOOM2.WAD`.

**Tech Stack:** Python stdlib, UDMF PWAD writer, Zandronum, Doom II IWAD on the local machine.

---

## Acceptance Criteria

1. Polygonal/irregular rooms are no longer only documentation: an `irregular_octagonal` room emits diagonal/chamfered linedefs in UDMF.
2. Stair access is represented by real intermediate-height sectors for raised platforms and pits.
3. Height-feature stair steps avoid overlap/crossing linedefs and keep adjacent floor changes within Doom's 24-unit step limit where the authored feature declares stair access/escape.
4. Starts, keys, items, and monsters avoid blocking height features.
5. Existing v0.4 safety gates remain green: no missing visible textures, no unknown flats/textures, no crossing linedefs, valid sidedef orientation.
6. `build/v05_blue_lock_processing.wad` exports and loads in Zandronum with real `DOOM2.WAD` without parser/log diagnostics.
7. README and version identify v0.5 accurately.
8. Local git commit captures the finished v0.5 state.

## Implementation Steps

### Task 1: Preserve current v0.5 safe placement

### Task 2: Add octagonal/irregular room test first

### Task 3: Implement chamfered room boundaries
- Modify `build_geometry_textmap()` and `_add_room_boundary()` to pass room shape.

- Keep rectangular rooms on the existing path.

### Task 4: Add stair-sector tests first
- Add a test that raised platforms and pits with stair access/escape emit intermediate floor heights beyond the base and final feature heights.
- Add a test that two-sided adjacent floor deltas do not exceed 24 for stair-connected height features.
- Run these tests and verify they fail before implementation.

### Task 5: Implement adjacent stair clusters
- Add a cluster helper in `UdmfBuilder` to emit adjacent inner rectangles and correctly convert shared feature edges to feature-feature two-sided lines instead of parent-sector boundaries.
- For raised platforms with `access: stairs`, emit one intermediate step sector plus the platform sector.
- For pits with `escape: stairs`, emit one intermediate step sector plus the pit sector.
- Keep pillars as blocking inner rectangles.

### Task 6: Full verification

### Task 7: Documentation and commit

## Risks

- Adjacent stair sectors can create duplicate or crossing linedefs if generated with the old isolated inner-rectangle helper. Use a cluster helper to own shared edges cleanly.
- Diagonal room edges can break the axis-aligned crossing test if the test assumes only vertical/horizontal lines. Keep the old crossing test for axis-aligned generated segments, and add positive diagonal coverage rather than overgeneralizing intersection code yet.
- Lifts require exact ZDoom special behavior. Do not fake a moving lift with an uncertain action special in the finished milestone; use stairs first because they are structural and reliable.
